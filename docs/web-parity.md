# 网页版替代范围与规划

状态：0.6 当前代码盘点与后续设计，2026-11-17。下列“计划”尚未实现，不代表已验证能力；当前界面继续使用原生控件、简短英文和分层设置。

开发者已能完成“预览 → 草稿 → 发布 → 收到审阅 → 更新 Diff”；审阅者已能完成“收件箱 → 看 Diff/公开讨论 → 总体/行内意见 → 保存/发布审阅和 Ship It”。
**目前最大的网页依赖是反馈处理闭环：回复、问题状态、草稿清理和请求关闭。** 应先补齐这些日常操作，再扩展高级比较和附件。

## 当前覆盖与缺口

| 工作任务 | 0.6 已有 | 仍需网页/其他工具 | 顺序 |
| --- | --- | --- | --- |
| 创建、更新代码审阅 | 冻结范围/只读预览、三种模式、审批人/组/Bug、上传/更新/发布、HEAD 绑定与部分写入恢复 | 附件、依赖关系等高级字段；请求/差异草稿丢弃 | A、C |
| 阅读与反馈 | 按 ID/My Requests、历史版本、公开全文/回复、行内定位、原生线程、总体/行内意见、Ship It | 回复写入、general 独立评论、issue 打开/解决/丢弃/重新打开/验证 | A |
| 管理自己的审阅草稿 | 本地意见缓存，保存/发布私有审阅，外部冲突保留文本 | 编辑/删除已保存行内评论、丢弃整个审阅草稿、撤销自己的 Ship It | A、B |
| 跟进审阅 | 待审队列、已读/未读、公开审阅/回复活动通知；自己发布的 pending 单收到反馈也提醒 | 自己请求的统一活动列表、关注/星标、搜索/筛选、关闭单的活动历史 | B |
| 判断是否可合入 | 公开 Ship It 及问题状态可从讨论读取 | 服务端 approved/approval_failure、聚合票数/问题计数、CI status updates 的紧凑显示 | B、C |
| 请求生命周期 | pending/public/draft 可读，发布字段与 Diff 核对 | 标记 submitted/discarded、重新打开、丢弃差异/元数据草稿 | B |
| 复审更新 | 选择任一已有 Diff 版本，对比各版本相对其基线的差异 | v1→v2 interdiff、逐提交视图/范围选择、修改历史 | C |
| 非代码文件 | 附件/截图评论及回复文字可读 | 文件上传/下载、图片/PDF/二进制预览和相关定位评论 | D |
| 团队特有流程 | 复用 RBTools 认证、原生 HEAD 标识；能力检查 | 公司权限/SSO/扩展字段/审批与 CI 规则适配 | 每批真实环境验收 |

本地 Git 提交/暂存由 VS Code Git 处理；合并/land/push 是另一个需要明确设计和授权的工作流，不应以插件 Ship It 或已读状态自动触发。
服务器 `approved` 才是其审批结论；团队扩展可能改变规则，不能由客户端硬编码“几个 Ship It 就批准”。[官方字段说明](https://www.reviewboard.org/docs/manual/latest/webapi/2.0/resources/review-request/)

## A：补齐评论处理闭环（下一批）

1. 原生线程/总体意见下新增 Reply，原生编辑器写入，先保存回复草稿，再独立发布；以请求、父审阅、父评论 ID 精确关联。
2. 原生线程的 issue 状态和操作菜单：Open / Resolve / Drop / Reopen；服务端支持时提供 Verify。每次按权限和当前状态提供操作，回读确认。
3. 支持编辑/删除自己未发布审阅中的已保存行内意见，丢弃整份私有审阅；公开评论保持不可改写。

验收：作者回复 → 审阅者收到更新 → 原线程显示 → 作者解决 → 审阅者验证/重新打开；跨用户、旧 Diff 评论、权限拒绝、超时恢复均覆盖。
删除前使用原生确认，写入保留现有 journal/不盲重试模式；新 Diff/外部编辑不能让回复落到错误评论。
Review Board 提供[回复草稿资源](https://www.reviewboard.org/docs/manual/latest/webapi/2.0/resources/review-reply-draft/)和[评论更新接口](https://www.reviewboard.org/docs/manual/latest/webapi/2.0/resources/review-diff-comment/)；实现时仍需在本地 7.0.6 和团队服务验证具体 issue 权限和状态转换，不把文档当作实际验收。

## B：补齐请求与审批管理

- Review 只增加一行紧凑的服务端 Approval/问题计数，详细原因按需展开，不引入复杂客户端审批状态机。
- 支持提交完成/放弃/重新打开请求，以及单独丢弃元数据/差异草稿；确认权限、当前版本与草稿影响，不进行 Git merge/push。
- 将 Inbox 扩为原生分组 Assigned / My requests / Activity，沿用服务器+账号+活动版本的阅读状态；支持筛选和按标题/ID 查找。
- 支持撤销自己的 Ship It；不提供“删除公开审阅”或“取消发布评论”这种服务端不允许的动作。[审阅资源的修改边界](https://www.reviewboard.org/docs/manual/latest/webapi/2.0/resources/review/)

验收：所有生命周期操作可回读确认，取消无写入；新通知不会被旧页面的已读事件吞掉，关闭/重新分配能退出旧队列；服务端拒绝与网络丢响应可恢复。

## C：复审和高级信息

- 使用原生 Quick Pick 选择两个版本，原生 Diff 查看 interdiff；保留真实 filediff/interfilediff 身份，不猜评论行位置。
- 按需设置依赖请求等低频字段，保留已有 Testing Done/Change Description，不重新占用日常提交视图。
- 读取服务端 status updates/CI 检查，并展示来源/时间；能力缺失时隐藏，不假设公司 CI 接口和审批阈值。

验收：跨版本增加/删除/重命名、parent diff、merge HEAD、历史评论定位正确；版本切换保留未保存意见，过期响应不覆盖新选择。

## D：附件与运行环境

逐步增加文件附件、图片预览和相关评论，之后再评估 PDF/特殊文件支持。认证继续走 RBTools；验证 Linux/WSL/SSH、团队证书/代理和服务版本矩阵，按服务能力降级。
真实推送通知需要服务端 webhook/中转接收端及身份/去重设计，暂不作为本地插件的隐式依赖。

## 0.6 的通知与一致性边界

当前使用客户端轮询：默认 60 秒、窗口获焦和手动刷新。官方 [last-update](https://www.reviewboard.org/docs/manual/latest/webapi/2.0/resources/review-request-last-update/) 提供公开 request/diff/review/reply 活动，**不包含私有请求草稿变更**；选中请求另读取自己可见的私有草稿和审阅草稿。统计字段补充 issue/Ship It 变化检测。

- 自动通知覆盖当前连接的分配待审单和自己公开的 pending 单；自己的草稿、未关注的任意单、已经关闭/离开待审查询的单没有完整历史通知队列。
- 首次同步静默；同一活动去重；活动读取失败不推进游标。离线时保留原有显示，日志记录失败，重连重试。
- 同一 Diff 更新元数据和公开讨论，保留本地输入；新 Diff 只提示 Open latest，旧代码快照不变。View All Comments 自动更新，单条全文是只读快照。
- 轮询不能保证逐条捕获两次检查之间的所有中间事件，VS Code 关闭时也不会接收推送。多服务器/账号同时订阅属于后续队列设计。
- 写操作仍重新核对内容和 Diff；后台刷新不会绕过 HEAD/patch 校验。跨多次 API 调用不存在服务器原子 CAS 保证。

本地验收使用隔离 Git/请求、Review Board 7.0.6、RBTools 7.0；公司 CI、最终合并与真实权限矩阵未在这里验证。每批交付均要区分实现、自动验证、团队环境待验收三种状态。
